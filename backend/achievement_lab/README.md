# تجربة الإنجازات محلياً

هاد التجهيز كيشغّل نفس `router` ديال اللعبة، حساب النقط والإنجازات، خدمات الحفظ والبثّ. غير المصادقة الخارجية كتتعوّض بوسيط خاص بتطبيق الاختبار. `main.py` ديال التطبيق العادي ما كيتبدّلش، وما كيقبلش هاد الرموز. هادشي **ماشي اختبار لـ`JWT` أو تسجيل الدخول الحقيقي**.

خاص `Docker` خدام، و`uv` موجود. الأوامر التالية من جذر المستودع، ففرع `sjoukni`:

```bash
backend/scripts/achievement_lab.sh start
backend/scripts/achievement_lab.sh status
backend/scripts/achievement_lab.sh demo
backend/scripts/achievement_lab.sh profile 101
backend/scripts/achievement_lab.sh verify-restart
```

`start` كينشئ حاوية `PostgreSQL 16` مستقلة باسم فيه بصمة مسار المشروع، وموسومة بـ`trivia.achievement-lab`. الاتصال بـ`127.0.0.1` فقط، والمنفذ كيتختار تلقائياً. كيطبق سلسلة `Alembic` حتى `a41d9e2c1001` على قاعدة `achievement_test_lab`، وكيضيف الحسابات والأسئلة بلا حذف التاريخ السابق. كاينين `3` فئات، `36` سؤال حسابي و`216` جواب خاطئ مخزنين فعلياً.

`demo` كيدخل خمسة لاعبين، كيضبط مباراة بجولة وحدة، كيختار الفئة والسؤال، كيقدم الخدع والأصوات بأحداث اللعبة العادية. اللاعب `101` كيصوّت للصحيح، والأربعة الآخرين كيصوّتو على خدعتو. كيربح `9` نقط و`4` أصوات خدعة. إعادة `demo` كتخلق مباراة جديدة؛ تكرار الحساب ما كيكرر صف الإنجاز.

`profile` كيقرأ الهوية والتاريخ والإنجازات من القاعدة عبر مسار تشخيصي خاص بتطبيق الاختبار: `GET /test/profile`. ماشي واجهة منتج ولا مسار تزاد فالتطبيق العام. `verify-restart` كيقارن بروفايلات الخمسة قبل وبعد تبديل عملية `Uvicorn` فعلياً، وكيكتب الدليل فـ`.achievement-lab/restart-evidence.json`. خاص مباراة محفوظة قبلو (`demo`). الغرف الحية ما كتسترجعش بعد إعادة تشغيل الخادم.

## الحسابات وطريقة الدخول

| المستخدم فقاعدة الاختبار | الاسم | رمز تجريبي علني |
| --- | --- | --- |
| `101` | `User101` | `lab-player-101` |
| `102` | `User102` | `lab-player-102` |
| `103` | `User103` | `lab-player-103` |
| `104` | `User104` | `lab-player-104` |
| `105` | `User105` | `lab-player-105` |

العميل كيبعت `Authorization: Bearer lab-player-101` مثلاً. الخادم كيربط الرمز بالمعرّف، واعتماد الهوية العادي كيتحقق من وجود المستخدم فقاعدة البيانات. `user_id` و`user_name` فالاستعلام أو الرسائل ما كيبدلوش الهوية. الرموز ماشي أسرار حقيقية، وماشي كلمات سر صالحة فالتطبيق العادي. وسيط الاختبار ما كيقبلش هوية مرسلة مباشرة من العميل.

باش تلعب يدوياً، حل خمسة أطرافية ونفّذ نفس الأمر بمعرّفات من `101` حتى `105`:

```bash
backend/scripts/achievement_lab.sh client --user 101 --room manual
```

هاد العميل كيعرض `JSON` وكيقبل رسالة فكل سطر؛ ماشي واجهة اللعبة. المضيف `101` يبدأ بهاد الرسائل:

```json
{"event":"UPDATE_SETTINGS","data":{"total_rounds":1,"bluff_time":60,"vote_time":60,"max_players":5,"language":"en"}}
{"event":"NEXT_PHASE","data":{}}
{"event":"GET_QUESTION","data":{}}
```

`GET_QUESTION` بلا فئة كيستعمل الفئة الافتراضية اللي جابها الخادم من القاعدة. فكل طرفية، من بعد `PHASE_QUESTION`، بعث خدعة مختلفة على الجواب الصحيح:

```json
{"event":"SUBMIT_BLUFF","data":{"bluff_answer":"جواب تجريبي"}}
```

من بعد `PHASE_VOTING` استعمل `id` فعلي من `choices` (ماشي النص):

```json
{"event":"SUBMIT_VOTE","data":{"choice_id":"ضع-هنا-id-الاختيار"}}
```

من بعد `RESULTS_REVEALED` بعث `NEXT_PHASE` باش توصل لـ`PHASE_PODIUM`. إلا بقى التعادل، `NEXT_PHASE` آخر كيبدأ جولة إضافية. إلا فشل الحفظ، الخادم كيبعث `PERSISTENCE_FAILED`؛ الرسالة ديال إعادة المحاولة هي:

```json
{"event":"RETRY_PERSISTENCE","data":{}}
```

الرسائل كتفرّق بين `unlocked_achievements` (تحقق الشرط فالمباراة) و`newly_saved_achievements` (إدراج أول مرة للمستخدم)، وكتعلن `persistence.status=saved` بعد نجاح المعاملة.

## تشغيل الاختبارات

```bash
# الاختبارات المعنية، باستعمال قاعدة المختبر مع schema معزول لكل اختبار
backend/scripts/achievement_lab.sh test

# غير المباريات اللي كتتلعب كاملة عبر الشبكة
backend/scripts/achievement_lab.sh test tests/test_achievement_journey.py

# المجموعة الكاملة، بما فيها مشاكل الغرف المعروفة
backend/scripts/achievement_lab.sh test tests app/dataProcessing/test.py

# بديل مؤقت: حاوية جديدة كتتحذف أوتوماتيكياً، مستقلة على التجربة اليدوية
backend/scripts/test_achievements.sh
```

السكريبتات كتستعمل `uv run --locked --group dev python -m pytest`. تجهيز الاختبارات السابق `database()` كيخلق `schema` عشوائي، كيطبق الترحيلات الفعلية، وكيحذف غير داك `schema` فالنهاية. الحسابات والتاريخ فـ`public` ديال المختبر كيبقاو متاحين. ما كاين حتى تنظيف لقاعدة المستخدم العادية.

`test_achievement_journey.py` كيستعمل `tcp_server()` الموجود، خمسة اتصالات فعلية، أسئلة القاعدة، ومؤقت التصويت الحقيقي ديال `10` ثواني فحالات غياب الصوت. ما كيعوض لا `calculate_results()` لا الحفظ لا المرحلة لا عدّادات التقدم. قراءة حالة الغرفة فالاختبار غير للتحقق، ماشي لتهيئتها.

الاستثناءات المقصودة:

- العتبات التاريخية: `seed_history()` كيزرع نتائج مباريات مكتملة فقاعدة الاختبار؛ هاد المباريات السابقة ما تلعبوش عبر الشبكة. المباراة الجديدة كتتلعب كاملة؛ الأكواد المستهدفة ما كيتزرعوش.
- `COLLECTOR`: كيتزرعو تسعة أكواد أخرى مختلفة، مع محاولة تكرارها. العاشر `BLUFFER` كيتفتح بجولة عادية. `COLLECTOR` نفسه ما كيتزرعش.
- فشل المعاملة: خطاف اختبار كينفذ `SELECT 1 / 0` وسط المعاملة، من بعد الإدراج. `PostgreSQL` كيدير التراجع فعلياً؛ من بعد كنحيدو الخطاف وكنرسل `RETRY_PERSISTENCE` عبر الشبكة.
- الاختبارات القديمة فـ`test_events.py` باقية اختبارات معزولة ببيانات مهيأة وخدمات حفظ معوضة. نجاحها بوحدو ماشي دليل الحفظ؛ الاختبارات الجديدة وخدمات `test_persistence.py` هي اللي كتستعمل قاعدة فعلية.

ما كايناش واجهة فهاد النسخة: استقبال `JSON` أو قراءة البروفايل ما كيثبتوش عرض إشعار أو بقاؤه بعد تحديث صفحة. مشاكل الغرف المستقلة كتتسجل فوثيقة المتابعة، وما كتختبئش بتغيير الاختبارات.

## الإيقاف والتنظيف

```bash
backend/scripts/achievement_lab.sh stop
backend/scripts/achievement_lab.sh start

# حذف بيانات المختبر فقط؛ الحسابات كتتخلق من جديد عند start من بعده
backend/scripts/achievement_lab.sh clean
```

`stop` كيوقف الخادم وحاوية المختبر وكيحتافظ ببياناتها. `clean` كيحذف الحاوية المحددة وأحجامها المجهولة فقط من بعد التحقق من الوسم؛ ما كيستعملش `docker prune` وما كيحذف حتى حاوية أخرى. الملفات `.achievement-lab/state.json` و`server.log` محلية ومتجاهلة فـ`Git`. إعادة `start` ما كتصفّرش إنجازات التجربة اليدوية.
